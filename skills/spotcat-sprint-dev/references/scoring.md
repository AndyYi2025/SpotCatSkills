# Review 评分细则

## 总体原则

- 每项打分 **0 到满分**，不允许负分
- ≥9 分才可进入下一任务
- <9 分必须记录具体扣分原因
- 评分必须客观，有据可查

---

## 各维度评分细则

### 1. 正确性 (满分 3.0)

| 分数 | 描述 |
|------|------|
| 3.0 | 功能完全对齐 API spec，无 bug，边界条件处理完整 |
| 2.5 | 功能完整，小问题 1-2 个边界条件未处理 |
| 2.0 | 功能基本完整，主要流程通，但有 1-2 个明显 bug |
| 1.5 | 核心功能有问题，API 对齐有偏差 |
| 1.0 | 功能不可用或严重偏离 spec |
| 0 | 完全无法运行 |

**检查清单:**
- [ ] API endpoint 正确
- [ ] HTTP method 正确 (GET/POST/PUT/DELETE)
- [ ] 请求/响应格式与 spec 一致
- [ ] 错误处理覆盖常见失败场景
- [ ] 边界条件处理 (空字符串、null、超长输入)

---

### 2. 代码质量 (满分 2.5)

| 分数 | 描述 |
|------|------|
| 2.5 | 类型完整、可读性极佳、无调试代码 |
| 2.0 | 类型基本完整，有少量问题或可读性问题 |
| 1.5 | 类型不完整 (>20% 缺失)，可读性一般 |
| 1.0 | 代码混乱，基本无类型 |
| 0 | 无法阅读 |

**检查清单（按语言）：**
- (TypeScript) 无 `any` 类型 (或 <10%)
- (Python) 无 bare `except`、无 `# type: ignore`
- (Go) 无 `_ = err` 忽略错误
- (通用) 变量/函数命名语义化
- (通用) 无调试代码 (console.log/print)
- (通用) 函数 < 50 行

---

### 3. 可维护性 (满分 2.0)

| 分数 | 描述 |
|------|------|
| 2.0 | 模块化清晰，文档完整，配置外部化 |
| 1.5 | 模块化尚可，文档基本够用 |
| 1.0 | 单体文件过长，文档缺失 |
| 0 | 无法维护 |

**检查清单:**
- [ ] 模块/文件结构合理
- [ ] 有使用示例或文档
- [ ] 配置常量外部化 (不硬编码)
- [ ] 重复代码 <3 处

---

### 4. 测试覆盖 (满分 1.5)

| 分数 | 描述 |
|------|------|
| 1.5 | 核心路径测试 >80% 覆盖 |
| 1.0 | 主要功能有测试，覆盖 >50% |
| 0.5 | 有测试但覆盖 <50% |
| 0 | 无测试 |

**覆盖优先级:**
1. API 调用正确性
2. 错误处理分支
3. 边界条件
4. 配置解析

---

### 5. 用户体验 (满分 1.0)

| 分数 | 描述 |
|------|------|
| 1.0 | 输出格式清晰、帮助信息完整、错误提示友好 |
| 0.7 | 输出基本清晰，错误提示尚可 |
| 0.5 | 输出生硬，错误信息不友好 |
| 0 | 无帮助信息，错误信息等于没有 |

**检查清单:**
- [ ] `--help` 输出完整
- [ ] 错误时显示原因和解决建议
- [ ] 成功/失败有明确视觉区分

---

## 综合评分计算

```
总分 = 正确性得分 + 代码质量得分 + 可维护性得分 + 测试得分 + UX得分
```

---

## SDD 评审分工

| Phase | 负责维度 | 门控 |
|-------|---------|------|
| Spec Reviewer | 正确性 (3.0) | ≥ 2.5 |
| Quality Reviewer | 代码质量 (2.5) + 可维护性 (2.0) + 测试覆盖 (1.5) + 用户体验 (1.0) | 总分 ≥ 9 |

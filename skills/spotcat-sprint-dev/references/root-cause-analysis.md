# 根因分析协议

## 执行环境

本 prompt 在 cron turn 内同步执行。

## 触发条件

满足以下任一：
- 同一任务连续 3 次 quality-review 得分 < 9/10（fail_streak ≥ 3）
- 同一任务连续 3 轮 cron implementer 测试不过
- 同一任务总轮次 > 10

**约束：本轮内完成分析，不跨 cron 等待任何外部响应。**

## 目标

找到根本原因（不是症状），采取针对性措施，避免盲目重试。

## 流程

### Phase 1: 收集数据

1. 读取 sprint-plan.md 中此任务的**最近 5 轮**交付记录
2. 提取每轮的 phase、门控结果、分数、扣分项
3. 列出重复出现的扣分维度和失败模式

### Phase 2: 识别根因

分析扣分模式，归类为以下 5 种根因之一：

| 根因类型 | 典型症状 | 识别信号 |
|----------|---------|---------|
| **需求不清** | 每轮扣分项不同，无固定模式 | 验收标准模糊或有歧义 |
| **任务过大** | 每轮只完成部分功能，总在正确性丢分 | 单个任务涉及 > 5 个文件 |
| **技术债务** | 反复在代码质量/可维护性丢分 | 依赖的外部代码质量差 |
| **架构问题** | 每轮改动互相矛盾，修复 A 导致 B 退化 | 改动涉及核心模块 |
| **环境问题** | 测试在不同时间通过/失败，与代码改动无关 | 外部服务不可用、依赖冲突、数据状态异常 |

### Phase 3: 采取措施

**本轮内完成，自主执行，不等待任何外部决策。**

根据根因类型：

**需求不清：**
- 直接更新 sprint-plan.md 中的任务描述和验收标准

**任务过大：**
- 在 sprint-plan.md 任务池中将此任务拆分为 2-3 个子任务

**技术债务：**
- 在任务池中插入一个 "清理债务" 子任务

**架构问题：**
- 记录到 `.learnings/LEARNINGS.md`
- 任务 phase 改为 `blocked`

**环境问题：**
- 验证环境健康
- 如果不可修复，记录到 `.learnings/ERRORS.md`，phase 改为 `blocked`

### Phase 4: 记录和重置

1. 将根因分析结果写入 `.learnings/LEARNINGS.md`

2. 更新 sprint-plan.md（按此顺序）：
   - rc_count = 当前 rc_count + 1
   - 轮次 +1
   - 判断 phase 走向：
     - 架构问题 → phase = blocked
     - 不可修复环境问题 → phase = blocked
     - 其他 → 执行修复措施，phase = implementing
   - 如果 phase 回到 implementing：重置 fail_streak = 0，重置 impl_fail = 0

## 终止条件

- 根因类型为"架构问题"或"不可修复环境问题"→ phase 改为 `blocked`
- 其他根因类型 → 自主修复后 phase 改回 implementing

## 输出格式

```markdown
### {任务名} — Phase: root-cause — 轮次 {N}

**门控:** PASS — 根因分析完成
**分数:** N/A

#### 扣分模式
| 轮次 | Phase | 总分 | 主要扣分维度 | 扣分项 |
|------|-------|------|-------------|--------|

#### 根因类型: {类型}

#### 分析过程
{为什么是这个根因}

#### 采取措施
{具体行动}

#### 判定
- next_phase: {implementing|done|blocked}
- root_cause_type: {类型}
- rc_count: {新值}
- fail_streak: 0（如重置）
- impl_fail: 0（如重置）
```

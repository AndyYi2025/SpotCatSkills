# SpotCat 项目目标

## 一句话定位

SpotCat 不是量化交易框架，不做策略研究方法论、不做券商对接、不做实盘执行引擎。它是给"一个人、多个量化
项目、用 Cron 驱动 agent 自动开发"这个场景提供的**可执行治理层**——管的是"这次开发流程和质量判断是否可
信"，不管交易逻辑本身赚不赚钱。

## 为什么存在

SpotCat 现在（重新设计前）100% 是 markdown prompt，没有一行可执行代码。所有"检查"最终都退化成"agent 说
它检查过了"。这在无人值守、7×24 跑 Cron 的场景下是致命的——没有人实时盯着每一轮 quality-review 的结论是不
是编的。

这个项目存在的意义，就是把治理规则从"写在 prompt 里、指望 agent 自觉"，变成"脚本判定，agent 无法覆盖"。
纯 advisory 的文字规则会被自主 agent 静默绕过；只有确定性的脚本 exit code、真实数据，才能提供"这次检查一
定发生了"的保证。

## 三类目标

### 1. 资金安全硬门

仓位限制、双层 kill switch（项目级+全局级）、防重复下单、凭证管理——这一类错了是真实亏钱或失控交易，不是
代码难看。判断标准不是"能不能脚本化"，而是"允不允许有任何 advisory 残留"：这里的任何一条都不能停留在"建
议 agent 检查"，必须是脚本判定，无条件否决。

### 2. 回测证据完整性

一个数字（Sharpe、回撤、胜率）不能只是 agent 读了一眼输出文件之后的转述，必须证明它来自脚本对真实回测输
出的解析。前瞻偏差、数据日期缺口、数据源被静默篡改——这些能让"看起来对"的回测结果实际上是假的，都要有对
应的机械检查拦住，而不是靠 agent 读代码时凭经验判断。

### 3. 代码/流程卫生（对应"控制 AI 生成文件膨胀"）

Agent 自主写代码时天然倾向于往现有文件里加而不是拆分，长期会长成没人管的巨型文件（这是从 megaview 项目
的真实教训里学到的：无约束时单文件涨到近 2000 行、单 feature 涨到近 3 万行）。LOC 预算棘轮、PARTIAL/
NOT_DONE 强制记录、安全检查优先于打分——这类改动出错代价最低，但决定了这套系统能不能长期维护下去而不是
半年后变成另一堆没人敢碰的 markdown。

## 边界：不做什么

- 不做具体的策略研究方法论（用什么因子、什么模型，是各量化项目自己的事）
- 不做券商 API 对接、不做实盘执行引擎
- 不假设任何特定回测框架（vnpy/nautilus_trader/custom 皆可，SpotCat 只认一份规范化的结果 schema，框架适
  配是各消费项目自己写的一次性 adapter）
- 不做团队级治理（RFC 审批流程、cell grid 之类）——目前是单人多项目场景，用不上

## 和其他文档的关系

- 本文档回答"为什么存在、目标是什么"，5 分钟读完
- `docs/architecture.md` 回答"skill 之间怎么协作、状态机长什么样"
- `docs/superpowers/specs/` 下的设计文档回答"某次具体重新设计要怎么建"（技术细节、取舍依据）
- `docs/superpowers/plans/` 下的实现计划回答"具体怎么写代码、按什么顺序、怎么验证"

优先级：本文档最少变，通常只在项目定位本身发生变化时更新；spec/plan 随每次具体设计/实现工作产生和归档。
